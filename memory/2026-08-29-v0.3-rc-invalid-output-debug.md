# V0.3 RC INVALID_OUTPUT 调试记录

## 假设

世界生成的真实响应可能在代码围栏/说明文字、JSON 截断、Schema 漂移、业务规则或 repair 预算之一失败；必须先区分层级，不能把所有失败归为同一 `INVALID_OUTPUT`。

## 实验与结果

- 追踪 Provider 到 SQLite：Prompt Schema 由 `AI_TASK_SCHEMAS` 生成，未发现 Prompt/TypeScript 版本漂移；Rust commit 独立复核 ID、validated output/world 一致性和业务规则后原子写入。
- 发现验证器仅执行裸 `JSON.parse`，会拒绝可确定规范化的围栏/唯一对象；修复后多个对象仍 fail closed。
- 发现 `finishReason=LENGTH` 在 parse 前未分类；现识别为 `RESPONSE_TRUNCATED` 并进入一次完整 repair/复验。
- 发现 repair Provider 失败会遮蔽初始验证字段路径；现以 cause chain 保留 INITIAL/REPAIR 和脱敏路径，同时最终错误仍保持真实 TIMEOUT 等分类。
- 发现世界构筑错误文案误用“已锁定硬结果”；已换成未提交世界阶段的准确说明。
- 三次隔离真实 DeepSeek 生产链路均在完整响应前 TIMEOUT，所以原截图的具体原始字段不可恢复，新的 parse/Schema/business/commit 真实验收为 `BLOCKED_EXTERNAL`。

## 结论

本地代码缺口与回归已闭合，但不能把真实 Provider 写成通过。隔离库和用户库均完整、无部分世界/unfinished/重复写入。需在 Provider 可用时重跑三组合，才可关闭总体 RC 状态。
