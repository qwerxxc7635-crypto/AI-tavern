## 1. 权限边界

Trait 点数是本地规则，不是生成内容的自评分。AI 可以为当前类型补写正面或负面效果文本，但不能选择 Trait 类型、分配点值、确认净点数或绕过开始门禁。SQLite 保存完整 `pointProfile`；任何显示值、AI 文本或序列化输入都必须再次经过 TypeScript 合同、Domain 规则和原生 Rust 边界验证。

本任务只判断结构是否合法及总点数是否严格归零。效果强度、公平性、触发频率、条件覆盖和 Trait 组合协同属于 M5-T05，不在本任务中推断或打分。

## 2. 合同

每项 Trait 可携带 version 1 `pointProfile`：

| 类型 | 正面效果 | 负面效果 | Buff 点 | Debuff 点 |
| --- | --- | --- | ---: | ---: |
| `BUFF` | 必填 | `null` | -5 至 -1 | 0 |
| `DEBUFF` | `null` | 必填 | 0 | +1 至 +5 |
| `MIXED` | 必填 | 必填 | -5 至 -1 | +1 至 +5 |
| `NARRATIVE` | `null` | `null` | 0 | 0 |

合同拒绝未知类型、未知字段、非整数、越界、错误符号、空效果和与类型矛盾的效果。`net` 不持久化，始终由 `buffPoints + debuffPoints` 本地计算；角色总点数是所有 Trait 净点数之和。

旧存档中缺少 `pointProfile` 的 Trait 按 `NARRATIVE / 0` 读取。这是只读兼容默认，不允许将带数值效果的旧描述反解析为点数。

## 3. 开始门禁与空集合

角色草稿可以保存非零或尚未完成的点数配置，以支持逐步编辑；此时会话保持 `ACTIVE`。进入 `READY_TO_CONFIRM` 及正式确认时，TypeScript 与 Rust 都必须重新验证全部 Trait，并要求角色总点数严格等于 0。

空 Trait 集合的总点数定义为 0，因此可以开始。当前角色创建页面延续既有纵向切片，最多编辑两项 Trait；共享合同和持久层允许 0 至 32 项，避免把 UI 上限误作领域规则。

## 4. UI 与 AI

角色创建页直接显示 Domain 规则的本地重算结果，并在配置非法或净点数非零时禁用“校验完整车卡”和确认。保存草稿保持可用，移除全部 Trait 后重新回到合法的净 0 状态。

类型选择与点数下拉框完全由玩家和本地规则控制。只有当前类型实际存在的 `positiveEffect` / `negativeEffect` 进入 M5-T03 的 `AIFieldAssist` 白名单；应用候选后再次比较类型和两类点数，任何变化都以 `RULE_AUTHORITY_CHANGED` 拒绝。界面继续复用现有角色创建布局、Design Tokens 和共享辅助组件，不建立第二套 UI 体系，也不提前执行 M10-T07 Legacy 迁移。

## 5. 序列化与兼容性

`pointProfile` 随既有角色和创建会话 JSON 持久化，不新增 SQLite 表或 schema migration。TypeScript Repository、SQLite 关闭重开和 Rust Native 创建/确认路径均验证同一结构与严格归零规则。

V0.2 `PlayerCharacter.traits` 从固定二元组兼容演进为数组，使 M5-T04 明确要求的空集合可以进入既有角色根记录。旧两项 Trait JSON 不变且继续读取；V0.3 Profile 投影只保留旧根字段 `id/name/description`，点数详情仍由完整 Profile 保存，不伪装成旧字段。portable `.emtavern` 仍是 v2，完整 V0.3 档案迁移继续留在 M10-T05。
