# Ember Tavern V0.3 产品与技术规格

版本：V0.3 Design Freeze

代号：Ember Rebuild

状态：冻结（后续实质性变更必须记录到 `docs/DECISIONS.md`）

基础版本：V0.2.0

## 1. 产品定义

Ember Tavern V0.3 是一个桌面优先、离线优先、可长期演化的单人 AI TRPG / RPG 世界。它应具备成熟 AI 角色扮演前端的角色、人格、世界信息、上下文、记忆、Prompt、预设和多角色场景能力，同时以本地规则引擎和 SQLite 持久化事实保证游戏结果、数值和世界连续性。

V0.3 不是 SillyTavern 的代码或界面复刻，也不是在聊天界面上附加 D20。产品目标是：让 AI 创建可成为世界事实并产生后续影响的内容，让程序裁决规则，让 SQLite 记住最终事实。

## 2. 不可破坏的原则

### 2.1 AI creates. Rules decide. SQLite remembers.

- AI 创作世界、NPC、职业、特质、装备语义、地点、势力、任务、事件、对话、行动候选和叙事。
- Rules Engine 裁决 D20、属性、技能、状态、装备强度、资源、金钱、时间、任务状态、Trait 平衡、伤害、死亡和合法性。
- SQLite 是游戏事实的唯一最终来源。UI 状态、模型上下文、缓存和模型会话都不是事实库。
- AI 输出必须依次经过结构验证、业务规则验证和原子持久化；模型不得直接写游戏状态。

### 2.2 创建阶段可刷新，游戏事实不可刷新

- 正式进入游戏前，世界、职业、特质、装备和其他未锁定候选可以反复生成。
- 游戏开始后，成功生成的 NPC 回复、D20 硬结果、任务成败、死亡和已经发生的世界事实进入不可随意改写的时间线。
- Retry 只用于网络失败、Provider 超时、Schema/解析损坏或与明确世界事实冲突。
- 技术 Retry 必须复用已锁定的硬结果和幂等键，不得借重试改变事实。

### 2.3 世界适应玩家

- 不提供固定主线脚本作为核心结构。
- 玩家可以忽略、拒绝、改变或自行创造目标，可以自由调查、交谈、交易、欺骗、离开和加入势力。
- AI 建议永远不是封闭动作列表；所有行动与对话场景保留自由输入。
- World Director 维护节奏和后果，不预写唯一剧情路线。

## 3. 范围与非目标

### 3.1 V0.3 范围

- Windows 桌面纵向切片优先；macOS 继续作为开发与共享质量平台。
- 正式 Design System、统一导航、错误架构和 AI 输入体验。
- 统一 Generator、Generation Queue、Structured Output 和 AI Inspector。
- World Constitution、Seed、Rules Engine、Knowledge Boundary。
- Quick / Advanced Character Creation、世界扩展字段和严格归零的 Trait 点数系统。
- 动态职业、装备、NPC LOD、地点和势力。
- 动态酒馆、多 NPC 场景、不可 Swipe 的正式回复和 Prompt Manager。
- 多任务 Quest Graph、World Director 和生成预算。
- Context Builder、结构化事实、近期/摘要/长期记忆和 World Lore。
- Lazy Generation、Prefetch、Streaming、Cache、Schema 版本和 V0.2 迁移。
- 三种世界的长流程可玩性、自由输入压力测试、完整审计和发布判断。

### 3.2 非目标

V0.3 不以以下能力为交付核心：TTS、图像或视频生成、多人联网、云同步、社交系统、Mod 商店、大规模插件生态、全面 iOS 客户端。可以保留小型接口边界，但不得因此延误核心版本。

## 4. 目标体验

```text
创建全新 AI 世界
→ 获得符合世界规则的职业与角色扩展
→ Quick 或 Advanced 车卡，所有自然语言字段可由 AI 辅助
→ Trait 净点数严格为 0
→ 快速进入动态酒馆
→ 与持久化、有限认知的一个或多个 NPC 互动
→ 使用 AI 候选或完全自由输入
→ 同时参与多个彼此影响的动态任务
→ 通过本地 Rules Engine 获得不可刷新的结果
→ NPC、势力、任务和世界继续演化
→ 保存退出、重启并准确继续同一世界
```

两个不同世界不得只是文案换皮；职业、社会、装备、Trait、NPC、任务和规则扩展必须明显不同。

## 5. 分层架构

```text
React / Tauri UI
  → Application Use Cases / Navigation / View Models
  → Generator Framework / Context Builder / World Director
  → Shared Domain / Rules Engine / Validation
  → Persistence and Native Ports
  → SQLite / Secure Credential Store / Provider Transport
```

依赖规则：

- UI 不直接执行 SQL、拼接核心 Prompt 或调用厂商 API。
- Application 只通过 Repository、Generator、Rules 和受限原生端口工作。
- Provider 是可替换生成器；业务类型不引用厂商 SDK。
- 设备 Credential 与页面生命周期分离；数据库和存档只保存引用。
- 重要状态变化必须生成可审计事件并在 SQLite 事务中提交。

## 6. 稳定性基础

### 6.1 Credential 生命周期

Provider 配置、Credential 引用和安全凭据由设备服务管理，React 页面状态只保存编辑草稿。设置 Key 后，世界、车卡、对话、任务、冒险、D20 叙事、保存、退出、重启和继续全过程必须仍可解析同一安全凭据。API Key 不得进入源码、普通配置、日志、SQLite、Inspector 或 `.emtavern`。

### 6.2 Navigation

使用统一 Router、Navigation History、Back 语义和必要 Breadcrumb。层级页不得各自发明返回逻辑。刷新/恢复必须从 SQLite 和路由参数恢复正确层级。

### 6.3 Error Architecture

统一错误分类：`ProviderError`、`GenerationError`、`ValidationError`、`PersistenceError`、`RuleError`、`NetworkError`。UI 提供与错误语义匹配的 Retry、Cancel、Fallback、Toast 和持久 Error State；不可重试错误不得伪装成可重试。

### 6.4 Performance Baseline

记录世界、NPC、任务、行动和 D20 叙事延迟，以及 prompt/output tokens、cache hit/miss、retry、queue wait。性能优化必须与同环境基线比较。

## 7. Design System 与交互

### 7.0 全局视觉规范与迁移优先级

`docs/EMBER_TAVERN_VISUAL_STYLE_GUIDE_V1.md` 是 V0.3+ 桌面 UI、UX 与 CSS 的全局视觉规范。统一方向为“黑暗奇幻酒馆 × TRPG 冒险手册 × 现代桌面游戏 HUD”：玩家首先感知游戏世界和活的角色，AI 只作为“命运 / 世界生成系统”出现，不呈现为 ChatGPT Clone、SaaS Dashboard、普通聊天软件或廉价页游式奇幻 UI。

视觉实现必须按 `Design Tokens → UI Primitives → Game Components → Feature Pages → Legacy UI Migration → Visual Consistency Audit` 渐进收敛。颜色、字体、间距、Border、Radius、Shadow 与 Motion 最终只能从 Design Token 获取；新增页面和自然修改到的 UI 在不扩大当前业务任务边界时立即遵循手册，既有页面差异记录在 `docs/V0.3_VISUAL_MIGRATION.md`，不得在无关业务任务中逐页返工。

发生冲突时，功能正确性、数据合同和存档兼容性优先；视觉表现尽可能遵循手册，无法兼容时必须记录设计决定。视觉迁移不得改变 Rules Engine、AI Provider、Generator/Queue、SQLite、Persistence、Save/Resume、Seed、Constitution、D20 或 Quest/NPC/Adventure 的业务合同和已验证状态机。

### 7.1 Tokens 与 Primitives

统一颜色、排版、间距、Border、圆角、阴影、动效、层级，并提供 Button、Input、Textarea、Select、Card、Modal、Drawer、Tabs、Tooltip、Toast、Skeleton、Progress、Empty State、Error State。Design Token 是上述视觉值的唯一基础来源；无障碍遵循 WCAG 2.2 AA 的适用要求并支持减少动态效果。

### 7.2 Game Components

复用 CharacterCard、NpcCard、TraitCard、QuestCard、ItemCard、ActionComposer、DialogueView、AIFieldAssist、GenerationPanel 和 StatusPanel；同类交互不得在不同页面复制实现。

### 7.3 AI Everywhere

所有玩家自然语言输入提供场景适配的 AI 生成、完善、候选、扩写、缩写、重新生成和锁定能力。AI 操作必须显示加载、取消、错误、采用/撤销状态，并读取已确定或锁定字段避免内部矛盾。

### 7.4 Action Composer

对话、调查和冒险统一使用 Action Composer：默认提供约 3–5 个上下文相关候选，同时永久保留自由输入。候选只是建议，不获得额外规则权限。

## 8. AI Generation Infrastructure

### 8.1 Generator 合同

统一 `Generator<T>` 生命周期：

```text
buildContext → buildPrompt → generate → parse → validate
→ repair → rulesCheck → persist → emitEvents
```

World、Character、NPC、Career、Trait、Item、Location、Faction、Quest 和 Event Generator 共用 Provider、错误、指标、Repair、幂等和持久化基础设施。

### 8.2 Generation Queue

- P0：玩家直接等待的 NPC 回复、Action、D20 narrative。
- P1：即将使用的任务、NPC 详情、当前地点。
- P2：NPC 预生成、地点扩展、世界事件、职业池等后台内容。

队列支持 priority、受控 concurrency、cancel、timeout、retry、fallback、deduplicate 和 metrics。取消或失败不得留下部分事实。

### 8.3 Structured Output 与 Inspector

重要实体必须有版本化 Schema；长文本不能是唯一数据结构。Inspector 可查看生成类型、Provider、模型、延迟、缓存、tokens、Context manifest、Prompt、原始输出、解析、验证和 Repair，但秘密与未授权世界信息默认遮罩，玩家模式不暴露调试内容。

## 9. World Constitution 与 Rules

### 9.1 World Constitution

每个世界保存版本化 `WORLD_CONSTITUTION`：世界类型、时代、科技、魔法、种族、社会、政治、经济、战斗尺度、死亡规则、职业规则、装备规则、NPC 规则、Trait 规则和禁忌。所有下游 Generator 必须携带并验证 Constitution revision。

### 9.2 Seed

世界 Seed 控制程序随机池、数值随机、事件抽样、地图初值和可程序化生成选择。LLM 文本不承诺完全确定性；Seed 不得替代已持久化事实。

### 9.3 Rules Engine

规则引擎是 D20、属性、技能、HP、状态、装备数值、金钱、时间、Trait、Quest、经济和资源的唯一裁决者。AI 只能提出受限提案。

V0.3 的具体本地 authority、命令闭集、事务审计、数值边界与 portable archive 限制见 [`V0.3_RULES_ENGINE.md`](V0.3_RULES_ENGINE.md)。

### 9.4 Knowledge Boundary

- `WorldTruth`：已授权的客观事实。
- `NpcKnowledge`：某 NPC 已知、怀疑、相信或误解的内容及 provenance。
- `PlayerKnowledge`：玩家已发现的信息。
- `Memory`：主观摘要，不能反向升级为 Truth。

NPC Context 只能包含该 Actor 合理可知的信息；省略本身不能被模型推断为真相。

V0.3 的四层持久模型、provenance、Actor 授权投影、迁移兼容与 portable archive 限制见 [`V0.3_KNOWLEDGE_BOUNDARY.md`](V0.3_KNOWLEDGE_BOUNDARY.md)。

## 10. Character Creation 2.0 与 Trait

### 10.1 Universal Character Schema

通用字段覆盖姓名、昵称、年龄、身份、种族/族群、出生地、阶层、信仰、外貌、性格、价值观、目标、恐惧、秘密、家庭、教育、重要人物、敌人、经历、职业、属性、派生属性、技能、熟练、能力、语言、财富、装备、声望、关系、Trait 和状态。

世界扩展通过版本化、受 Constitution 约束的字段定义表达，例如修仙的灵根/境界/宗门、调查世界的理智/幸运/信用、Cyberpunk 的义体/神经负荷/街头声望。扩展字段不得绕过通用数值与验证边界。

V0.3 的通用角色合同、世界扩展字段定义、V0.2 兼容投影、资源边界与迁移限制见 [`V0.3_UNIVERSAL_CHARACTER_SCHEMA.md`](V0.3_UNIVERSAL_CHARACTER_SCHEMA.md)。

### 10.2 两种模式

- Quick Creation：一句角色概念生成完整、合法、可编辑角色。
- Advanced Creation：编辑所有通用和世界扩展字段。

生成单字段、区域或整卡时读取已锁定字段；“重新生成未锁定内容”不得改写锁定内容。

两种模式的共享草稿、持久会话、锁定、Quick provenance、本地数值 authority、确认事务与恢复边界见 [`V0.3_CHARACTER_CREATION.md`](V0.3_CHARACTER_CREATION.md)。

### 10.3 Trait Point System

- Buff 消耗点数（通常 -1 至 -5）。
- Debuff 提供点数（通常 +1 至 +5）。
- Mixed 分别记录正负效果并计算净值。
- 0 Point Narrative Trait 不产生规则收益。
- 无 Trait 合法，空集合净值为 0。
- 开始游戏时所有 Trait 净点数必须严格等于 0。

`TraitBalanceValidator` 评估频率、环境、战斗、社交、剧情、经济、永久性、可规避性、稀有度和条件；`TraitSynergyValidator` 检查组合套利。AI 只建议点数，Rules Engine 最终裁决。

十维声明、透明分档、协同标签、生成反馈、兼容与确认门禁见 [`V0.3_TRAIT_POINT_SYSTEM.md`](V0.3_TRAIT_POINT_SYSTEM.md)。

## 11. Dynamic World Entities

### 11.1 Career

创建世界时生成符合 Constitution 的 Career Pool，分常见、少见、稀有和特殊。职业结构包含 role、skills、equipment、social position、relationships、risk 和 requirement；固定四原型不再作为玩家可见核心设计，但可保留迁移兼容映射。

Career Pool 的合同、Constitution 证据、P2 生成、SQLite 事务、角色引用与 V0.2 映射见 [`V0.3_DYNAMIC_CAREER_POOL.md`](V0.3_DYNAMIC_CAREER_POOL.md)。

### 11.2 Equipment

AI 负责名称、外观、历史、来源、剧情能力和语义效果；Rules Engine 负责 damage、defense、rarity、price、numeric bonus 和 balance。装备可成为线索、识别物、事实和关系触发器。

语义/数值分层、Constitution 证据、Quest 风险上限、受限绑定、原子结算、兼容持久化与 portable save/import 见 [`V0.3_SEMANTIC_EQUIPMENT.md`](V0.3_SEMANTIC_EQUIPMENT.md)。

### 11.3 NPC LOD

- LOD0：背景人口。
- LOD1：名字、外貌、当前行为。
- LOD2：职业、人格、目标、基本知识和关系。
- LOD3：完整长期记忆、秘密、关系网、任务、目标、装备和经历。

LOD 升级由互动重要性触发并持久化；已有字段必须延续，不得每次重新生成另一个 NPC。

LOD0–3字段解锁、Constitution绑定、知识引用白名单、逐级晋升、幂等事务、既有完整NPC兼容与后续动态酒馆边界见 [`V0.3_NPC_LOD.md`](V0.3_NPC_LOD.md)。

### 11.4 Location

地点覆盖国家、城市、村庄、酒馆、商店、遗迹、地下城和特殊地点。已有 WorldBible 地点先投影为 Outline，后续只在明确的 CHILDREN 或 CONNECTED 请求中渐进具体化；层级、连接、当前位置和旅行历史均由本地 SQLite 验证并持久化，不生成完整地图。

地点合同、Constitution 证据、渐进物化、拓扑门禁、移动事务与兼容边界见 [`V0.3_DYNAMIC_LOCATIONS.md`](V0.3_DYNAMIC_LOCATIONS.md)。

### 11.5 Faction

势力至少包含 Goal、Resource、Leadership、Enemy、Ally、Territory、Current Action 和 Player Relation，并可通过受预算的行动改变世界。

Faction OUTLINE/ACTIVE 投影、八项字段、关系对称、行动成本、预算 envelope、Quest/World Fact 后果、事务持久化与 World Director 后续边界见 [`V0.3_ACTIVE_FACTIONS.md`](V0.3_ACTIVE_FACTIONS.md)。

## 12. Tavern Rebuild

酒馆在当前世界、地点、时间、势力、事件和玩家历史上动态投影 NPC 与机会，不依赖固定名单。重要互动使 NPC 成为持久实体。

人口 Context、稳定来源身份、机会投影、LOD 聚焦、schema 19 事务、空状态、关闭重开与后续多 NPC Scene 边界见 [`V0.3_DYNAMIC_TAVERN_POPULATION.md`](V0.3_DYNAMIC_TAVERN_POPULATION.md)。

多 NPC Scene 根据知识、性格、关系、目标和场景决定谁说话、打断、沉默、偷听、离开或介入，不机械轮流。成功生成的正式回复进入时间线，不提供正常 Swipe。Prompt Manager 区分可编辑内容和不可被用户覆盖的 Core Rule Prompt。

逐 Actor Context、行动提案、本地仲裁、schema 20 事务、并发与 Tavern UI 复用边界见 [`V0.3_MULTI_NPC_SCENE.md`](V0.3_MULTI_NPC_SCENE.md)。正式回复锁定、技术 Retry、事实冲突恢复、schema 21 事务与 UI 规则见 [`V0.3_IMMUTABLE_NPC_TIMELINE.md`](V0.3_IMMUTABLE_NPC_TIMELINE.md)。公开 Context、3–5 条建议、schema 22 派生缓存、精确失效与自由输入边界见 [`V0.3_DIALOGUE_SUGGESTIONS.md`](V0.3_DIALOGUE_SUGGESTIONS.md)。

Core Rule 与 User Guidance 的固定顺序、preset/version、设备级事务、导入导出安全、缓存修订和默认恢复见 [`V0.3_PROMPT_MANAGER.md`](V0.3_PROMPT_MANAGER.md)。

## 13. Quest Graph 与 World Director

### 13.1 Quest Pool

允许世界事件、NPC 委托、势力任务、个人任务、隐藏任务、长期任务、紧急事件和玩家行为任务同时存在。状态闭集至少为：`HIDDEN`、`DISCOVERED`、`AVAILABLE`、`ACTIVE`、`BLOCKED`、`UPDATED`、`COMPLETED`、`FAILED`、`EXPIRED`、`ABANDONED`。

Quest Pool 的状态机、V0.2 `ACCEPTED` 兼容态、schema 23 真相源/append-only 转换账本、玩家直接介入、多 Active Quest、终态不可逆与迁移边界见 [`V0.3_MULTI_QUEST_POOL.md`](V0.3_MULTI_QUEST_POOL.md)。

### 13.2 Quest Graph

任务通过世界事实、实体、前置条件和后果边共享状态。一个任务改变势力、地点或 NPC 后，依赖任务必须由本地规则重新评估。玩家实际介入可以直接激活任务，不强制传统接受按钮。

边闭集、AND 前置语义、priority 冲突、稳定拓扑求值、schema 24 修订/求值账本、事务触发和只读调试投影见 [`V0.3_QUEST_GRAPH.md`](V0.3_QUEST_GRAPH.md)。模型不得声明依赖满足或目标状态，Quest 终态和既有业务合同保持不变。

### 13.2.1 Dynamic Quest Sources

NPC、Faction、World Event、Discovery、Player Action 与 Quest Graph Consequence 可以把已经提交的 SQLite 发生记录适配为 Quest 内容生成请求。来源、可见性、初始状态、公开 NPC/事实白名单、Constitution revision、同步安全预算和 provenance 均由本地规则决定；Generator 只返回内容候选。相同来源只能原子创建一个 Quest，隐藏 Quest 不进入玩家 Quest Board、生成历史或 Windows 图投影。完整合同、schema 25、去重、知识边界与后续 Director 分工见 [`V0.3_DYNAMIC_QUEST_SOURCES.md`](V0.3_DYNAMIC_QUEST_SOURCES.md)。

### 13.3 World Director

Director 评估世界变化、NPC/Faction 行动、机会、节奏、伏笔、压力、自然失败与过期，不写固定主线。预算限制 Active Quest 数、每日新增事件、高紧迫事件、NPC 主动频率和后台变化数；预算和冷却由规则层裁决。

M8-T04 的本地确定性评估、压力分段、过载收敛、最多八项提案、Rules/Generator/Faction Rules 路由、显式触发调度、context digest 重验及 schema 26 append-only 决策账本见 [`V0.3_WORLD_DIRECTOR.md`](V0.3_WORLD_DIRECTOR.md)。Director 不直接写事实，也不拥有模型调用循环。M8-T05 以 Rules Engine 游戏分钟为唯一时钟，提供 Active Quest、每日/紧急事件、NPC 主动与后台变化的持久预算、cooldown、延迟原因和防饥饿队列；完整合同见 [`V0.3_DIRECTOR_BUDGET.md`](V0.3_DIRECTOR_BUDGET.md)。玩家 P0 操作不进入该预算通道。

## 14. Context、Memory 与 World Info

统一 Context Builder 按以下逻辑装配最小相关上下文：

```text
System → World Constitution → Relevant Lore → Current Location
→ Player State → Actor Knowledge → Relevant Quests/World State
→ Long-term Memory → Recent Interaction → Current Action
```

模型不接收整个数据库。系统区分 Structured Fact、Recent Memory、Summary、Long-term Memory 和 World Lore；保留可替换检索接口但 V0.3 不以向量数据库为前置条件。预算、裁剪、稳定前缀、动态尾部和省略原因必须可审计。

M9-T01 已将 Windows 全部生产 Generator、Application 回合编排与 primary AI task 迁移到同一个分层入口。任务适配器先做 Campaign/Actor/Quest 相关性与知识授权投影，统一构建器再按上述顺序生成 immutable blocks/manifest，执行逐层相关性、预算、credential/full-database dump 门禁，并在 primary/fallback/repair 之间冻结一次。完整合同见 [`V0.3_UNIFIED_CONTEXT_BUILDER.md`](V0.3_UNIFIED_CONTEXT_BUILDER.md)。本阶段不生成新 Memory，也不提前实现 M9-T02/T03。

M9-T02 明确五层数据权威：Structured Fact 复用 Truth/Claim/Actor Knowledge，Recent 始终引用原 Message/Event/Turn，Historical Summary 与 World Lore 保存来源快照和 generation provenance，Long-term Memory 继续使用 Actor-scoped `Memory`。派生内容在来源删除/更新后变为 stale 并退出 current-only 投影，不删除原历史、不自动升级 Truth。schema 28、本地恢复与兼容边界见 [`V0.3_MEMORY_LAYERS.md`](V0.3_MEMORY_LAYERS.md)。

M9-T03 以结构化 Campaign/text/entity/Location/Quest query、版本化 Lore trigger rule、确定性 priority/score/token budget、完整 inclusion/omission manifest 和 query+corpus digest LRU 完成无向量依赖的 World Info 检索。SQLite adapter 是当前 candidate source，未来 RAG 只能替换该 port，不能绕过本地选择、知识权限或 Context Builder。NPC 对话已通过既有 `LORE` 层消费选择结果；完整合同和 schema 29 边界见 [`V0.3_WORLD_INFO_RETRIEVAL.md`](V0.3_WORLD_INFO_RETRIEVAL.md)。

## 15. Performance、Persistence 与 Migration

### 15.1 Lazy Generation / Prefetch / Streaming

新世界先生成可进入游戏的核心骨架，再按需或后台具体化。Director 可预取即将需要的 NPC、建议、地点、事件和 Quest Context。长文本交互支持可取消 Streaming，但只有完整验证并提交后的结果才成为事实。

Streaming 采用可选 Provider 能力：原生 SSE/Tauri Channel 只传输有序临时片段，非流式 Provider 保持完整响应路径。结构化输出只投影玩家可见字段；所有片段必须与 final content 完全一致，并在既有 Schema/业务规则验证后一次提交。NPC 使用 durable timeline 区分 pending、failed 与 committed，取消、超时或畸形 final 不产生正式消息。实现与验收详见 [`V0.3_STREAMING.md`](V0.3_STREAMING.md)。

M10-T01 将核心骨架固定为锁定 Constitution、World Seed、World Bible 与 outline Location/Faction；确认世界时只持久化 schema 30 具体化计划，不生成职业池、酒馆、NPC、Quest、Item 或完整地点。职业池、酒馆和阵容在既有真实提交事务完成后才收敛计划；失败、取消、重复请求、响应丢失与重开由 revisioned plan 和 append-only transition 恢复，SQLite trigger 拒绝用占位内容标记成功。P2 地点/势力只成为后台候选，预测与执行严格留给 M10-T02。完整合同见 [`V0.3_LAZY_WORLD_GENERATION.md`](V0.3_LAZY_WORLD_GENERATION.md)。

M10-T02 只从已通过 Director Budget admission 的 run 和 schema-30 后台资格计划中确定性预测：批准目标为 P1，其余候选受剩余 background capacity 约束为 P2，每轮最多四项且任何未完成 P0 都会抢占并失效预取。生成体只存在进程内；schema 31 仅保存身份、状态、审计和命中/耗时指标。只有 Campaign、kind、target、context digest 精确命中后，原 Feature 事务才可采用候选并重新执行既有业务验证/提交；未采用结果、隐藏来源和玩家猜测永不成为事实。完整合同见 [`V0.3_PREFETCH.md`](V0.3_PREFETCH.md)。

### 15.2 Cache

继续使用 Stable Prefix + Dynamic Tail，并优化 World Constitution、Stable Rules 和 Stable Prompt 的字节稳定性。记录 hit、miss、ratio、prompt/output tokens 和 latency；会话观察命中与 Provider 计费缓存必须明确区分。

### 15.3 Save Schema

存档保存 `save_schema_version` 与 `world_schema_version`。V0.2 → V0.3 迁移必须先备份、在隔离副本迁移、执行结构和领域重载验证，再原子切换；无法迁移时保留原件并明确报告，禁止静默损坏。尽最大合理努力兼容 V0.2 已有存档。
