## 1. Five distinct layers

Memory is not a second truth database. V0.3 keeps five layers with different authority:

| Layer | SQLite authority | Meaning |
| --- | --- | --- |
| Structured Fact | `world_truths`, `knowledge_claims`, `actor_knowledge` | Objective Truth, subjective Claim, and exact Actor authorization |
| Recent | original `messages`, `game_events`, `adventure_turns` | Immutable or revision-observable recent evidence; never copied only to make a Prompt |
| Summary | `historical_summaries` + source snapshots | A lossy, derived compression over retained source history |
| Long-term Memory | `knowledge_memories` + source snapshots | Actor-scoped subjective memory generated only from that Actor's authorized Knowledge/Event sources |
| World Lore | `world_lore_entries` + source snapshots | Source-backed setting exposition; not Truth and not retrieval configuration |

`HistoricalSummary`, `Memory`, and `WorldLoreEntry` cannot carry a Truth authority. `WorldTruth.authority` remains closed to local rule, user acceptance, domain transaction, and import; AI output cannot promote Summary, Memory, Claim, or Lore into Truth.

## 2. Source snapshot and drift

Every newly committed derived artifact freezes 1–128 ordered source snapshots. A snapshot contains only:

- closed source kind and source ID;
- source revision;
- SHA-256 of the stored source row;
- canonical source occurrence/update time.

Supported sources are World Truth, Claim, Actor Knowledge, Long-term Memory, World Fact, Game Event, Message, and Adventure Turn. The repository resolves the source directly from SQLite, checks Campaign and Actor ownership, and recomputes the digest inside the save transaction. A generated artifact may optionally reference its validated `generation_records` row, which must belong to the same Campaign.

Reading content and reading freshness are separate. If a source disappears, the artifact is `STALE / SOURCE_DELETED`; if revision, row hash, or source time changes, it is `STALE / SOURCE_UPDATED`. Current-only projections exclude stale artifacts. They do not delete or rewrite the original source rows, and they do not silently regenerate.

## 3. Summary lifecycle

A Historical Summary has a closed scope (`CAMPAIGN`, `ACTOR`, `ADVENTURE`, or `CONVERSATION`), coverage interval, source digest, generation record, revision, and creation/update time. Only `ACTOR` scope may carry an Actor identity, and it must resolve to that Campaign.

Creation requires revision 1 and expected revision 0. Rebuilding after source drift must explicitly capture the current sources and advance the artifact revision by exactly one. Old Message/Event/Turn/Fact rows remain in SQLite, so a Summary is never the only history and can always be audited against its cited evidence.

## 4. Actor Long-term Memory

The existing schema-12 `Memory` remains the only universal Long-term Memory entity. It requires an NPC or Player Character, creation time, and Knowledge/Event sources. Schema 28 additionally records immutable source snapshots for each new Memory. The writer is idempotent for the same identity/content and rejects identity collisions.

`EXTRACT_MEMORIES` still validates bounded transcript citations, but M9-T02 now also requires durable Actor Knowledge/Event sources before generation. Successful extraction keeps the legacy `NpcMemory` compatibility projection and writes the source-backed universal Memory. TypeScript and native NPC context select only current universal Actor memories; if an older save has no current universal memory, they conservatively fall back to the isolated legacy NPC list.

An Actor Summary or Long-term Memory cannot cite another Actor's Knowledge/Memory. Knowledge revision changes make the dependent Memory stale rather than rewriting its recollection or upgrading it to Truth.

## 5. World Lore boundary

`WorldLoreEntry` stores a bounded title/text, exact source snapshots, optional generation record, revision, and timestamps. It is setting exposition derived from already stored evidence. M9-T02 deliberately does not add Lore trigger rules, relevance scoring, priority, token allocation, cache keys, or a vector index. M9-T03 adds those selection concerns without changing Lore authority; see [`V0.3_WORLD_INFO_RETRIEVAL.md`](V0.3_WORLD_INFO_RETRIEVAL.md).

## 6. Persistence and recovery

Schema 28 adds:

- `historical_summaries`;
- `world_lore_entries`;
- `memory_artifact_sources` shared by Summary, Long-term Memory, and World Lore.

Local SQLite reopen preserves all artifacts. Internal snapshots now include the four schema-12 knowledge tables and all schema-28 memory tables in dependency order; older snapshot payloads treat them as empty. Snapshot restore returns the exact source rows and current/stale result.

Portable `.emtavern` remains format v2 and intentionally does not yet contain the general knowledge or memory-layer tables. The cross-language V0.3 archive upgrade, historical fixtures, corruption/interruption handling, and recovery UI remain one coherent M10-T05 change. Local reopen/internal snapshot evidence must not be described as portable round-trip support.
