# V0.3 Structured Entity Schemas

## Scope

M3-T03 establishes generation-boundary schemas for nine important V0.3 entity families: World Constitution, Career, Trait, Item, Location, Faction, NPC LOD, Quest Graph, and Director Action. These contracts describe structured proposals; they do not create tables or publish game facts.

Each registry entry has an explicit `schemaVersion` and separate strict input/output Zod schemas. The version is also present inside both payloads, so stored or transported payloads cannot be interpreted without checking it. Version 1 rejects missing fields, unknown fields, unknown enum values, and any version other than 1.

## Structural limits

| Entity | Maximum generated resources |
| --- | ---: |
| Career | 24 careers |
| Trait | 12 traits, 8 effects per trait |
| Item | 24 items |
| Location | 32 locations |
| Faction | 16 factions |
| NPC LOD | one NPC projection; bounded field lists |
| Quest Graph | 24 quests and 96 edges |
| Director Action | 32 proposals |

Shared identifier lists are capped at 64, general semantic lists at 24, identifiers at 128 characters, labels at 200 characters, and descriptive fields at 4,000 characters. Input request counts use the same family limits.

## Validation boundary

Schema parsing proves only that a payload is finite, recognized, and structurally interpretable. It intentionally does not prove that:

- references point to entities in the current campaign;
- an NPC LOD transition is allowed or preserves every existing fact;
- Trait points balance or Item numeric effects are legal;
- Quest transitions and edges are valid for current SQLite state;
- a Director proposal fits the remaining budget or cooldown.

Those checks belong to the Rules/Domain stages after parsing. A structurally valid proposal still cannot write SQLite directly.

## Cross-language contract

`entity-schema-contract.fixture.json` contains one valid input/output pair for every registry kind. TypeScript parses every pair through the authoritative Zod definition. Rust consumes the same file with a closed entity enum, strict fixture envelope, version check, required output discriminator, and matching top-level resource limits. This locks the desktop native boundary without duplicating the entire Zod business-independent schema in Rust.

Breaking changes require a new schema version and an explicit compatibility path. Unknown fields and versions must fail; they are never stripped or coerced into the current contract.
