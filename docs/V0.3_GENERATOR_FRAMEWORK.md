# Ember Tavern V0.3 Generator Framework

## 1. 生命周期

`packages/ai-core/src/generator.ts`定义与厂商、领域和数据库无关的`Generator<…>`：

```text
BUILD_CONTEXT → BUILD_PROMPT → GENERATE → PARSE → VALIDATE
→ REPAIR（仅首次 parse/validate 失败）→ RULES_CHECK
→ PERSIST + EMIT_EVENTS（同一事务）
```

每个边界是独立方法且可替换；`GeneratorRunner`只负责编排、一次repair、失败短路、事务端口和审计。Context、Prompt、Provider raw、parsed、validated、rules-checked、persisted与event使用不同泛型，避免结构parse被误当成业务规则或已持久化事实。

Repair最多一次，只能响应PARSE或VALIDATE失败；修复结果必须重新parse和validate，不能跳过RULES_CHECK。任何前置失败都不会调用后续规则、持久化或事件。未知异常仅投影`GENERATOR_STAGE_FAILED`，审计不保存原始异常message、Prompt、Context、raw response或秘密。

## 2. 事务与幂等

框架不导入Persistence或SQLite，只接受`GeneratorTransactionPort.run`。`persist`和`emitEvents`在同一事务回调；事件失败时由端口回滚事实与事件。Persist返回`COMMITTED`或`ALREADY_COMMITTED`：重放已提交幂等键时返回既有值并跳过emit，防止重复事件。

具体Application adapter仍负责Repository、事务实现、业务事件ID和聚合revision。框架不会直接写DB，也不会替代现有PendingAiRequest、GenerationRecord、Turn commit或Event Ledger。

## 3. 审计合同

每个阶段产生不可变的`GeneratorAuditEntry { sequence, stage, status, code }`，status仅为STARTED/SUCCEEDED/SKIPPED/FAILED。可选observer实时接收失败轨迹；成功结果携带完整audit、persistenceStatus和本次新事件。PERSIST事务范围包含EMIT_EVENTS，因此审计中PERSIST的SUCCEEDED在事件成功之后出现。

executionId与idempotencyKey使用有界格式，在任何stage调用前验证。错误由`GeneratorLifecycleError`保留失败stage、安全code与内部cause；cause不进入audit或玩家文案。

## 4. 首个迁移切片

Windows `DesktopAIOrchestrator.executeWithSelection`迁移到`DesktopStructuredGenerator`，继续使用原来的：

- Model Settings选择与fallback策略；
- `formatTaskPrompt`/稳定cache prefix；
- 唯一`AIProvider.generate`栈（Fake或Tauri native adapter）；
- `validateAIOutput`和同模型一次结构修复；
- native model selection drift检查。

该桌面层的PERSIST阶段只是把通过规则的候选结果交还Application，不保存游戏事实，EMIT_EVENTS为空；后续现有Application/Gateway仍执行结构/业务验证和原子提交。这保持“AI不能直接保存”并避免提前迁移全部World、Character、NPC、Quest和Adventure生成器。后续切片复用同一Runner，不能另建Provider栈。

## 5. 验证

框架测试覆盖无repair顺序、失败短路、安全审计code、validation repair与重新验证、规则拒绝、事件失败事务rollback、幂等重放不重复事件和非法execution身份。桌面测试覆盖repair阶段轨迹、skipped repair、Provider/Model选择、cache、fallback与生产服务仍仅通过共享编排facade；既有AITurn事务/repair回归同时执行。

## 6. Career Pool P2 切片

M6-T01 的 `GENERATE_CAREER_POOL` 复用本框架及单一桌面 Provider 编排，并进入 M3-T02 已建立的 Generation Queue P2 通道。相同世界、生成模式、Constitution revision、池 revision 和 rarity 请求使用同一 intent key 去重；队列取消/超时后在 Native 提交前复核 signal，不能留下迟到事实。结构输出仍须经过本地 Career Domain 校验与 Native 原子事务，不能把 Generator 的已验证候选误当成已持久化职业。

## 7. Semantic Equipment 结算切片

M6-T02 的 `GENERATE_ITEMS` 复用统一 Provider、Prompt、schema registry、Context Budget 与 generation audit。当前纵向切片在玩家等待的成功结算中生成一件 Quest reward；输入只开放语义字段、精确 Constitution 证据和本地列出的 Quest/NPC/Fact 绑定目标。结构通过后仍必须由 Domain/Native 根据 Quest risk、reward tier、主推荐属性和类别派生全部数字，随后与结算状态在同一事务提交。Generator 不拥有 price、damage、defense、bonus、物品归属或触发事实。

## 8. NPC LOD 按需具体化切片

M6-T03 的 `GENERATE_NPC_LOD` 只晋升一个已持久身份一级。Native 从当前 profile、锁定 Constitution 和 Actor Knowledge 构造 canonical 输入及引用白名单；Windows 统一 Generator 只产生候选，Domain/Native 再检查身份延续、字段解锁、引用权限和 expected revision。generation audit、profile 更新和 append-only transition 在同一 immediate transaction 中提交；同一 NPC 的并发调用由服务合并并最终由 SQLite revision 仲裁。LOD0 只能显式按需创建，Generator 不扫描或生成完整世界人口。

## 9. Dynamic Locations 渐进物化切片

M6-T04 的 `GENERATE_LOCATIONS` 每次只响应一个显式 `CHILDREN` 或 `CONNECTED` 请求，数量限制为一至八。Native 从当前地点图、锁定 Constitution 与 WorldBible Faction ID 重新构造 canonical 输入；Domain/Native 校验数量、证据、引用、规范化去重、父子拓扑和连接。generation audit、DETAILED 地点及连接在同一 immediate transaction 提交，相同扩展意图由 Windows 服务合并并最终由 SQLite 幂等键仲裁。初始 WorldBible 地点只作 OUTLINE 投影，Generator 不生成完整地图；旅行是独立的本地 revision 事务，不调用模型。

## 10. Active Factions 渐进激活切片

M6-T05 的 `GENERATE_FACTIONS` 只激活一至十六个明确请求的既有 WorldBible Faction。Native 从 OUTLINE 投影、锁定 Constitution 与本地 Faction/Location 白名单重建 canonical 输入；模型必须延续身份、Goal、Player Relation、既有 Territory/关系和四项 Constitution 证据。Domain/Native 再验证八项字段、规范化去重与 Ally/Enemy 双向一致，generation audit 与所有档案在一个 immediate transaction 提交。

Faction action 不调用 Generator。PLAYER、WORLD_EVENT 或未来 DIRECTOR 只能提交结构化 proposal 和不高于本地上限的预算 envelope；Native 重新计算资源、目标、成本、Quest 合法迁移及 World Fact 限额并原子持久化。M8 才实现 Director 的每日调度、持久预算与 cooldown，不能用 AI 输出绕过 M6-T05 的本地行动规则。

## 11. Dynamic Tavern Population 本地投影

M7-T01 不新增人口 Generator。World、Location、Clock、ACTIVE Faction、Event 与 History 已经是本地事实，人口层只把这些事实映射到稳定的 NPC LOD 身份和机会。首次出现的动态来源创建 LOD0 seed；只有玩家聚焦该身份时才复用 `GENERATE_NPC_LOD` 晋升一个等级。同一上下文不会重生名单，人口 state/member/cycle/focus 与 LOD profile 在 SQLite 事务中持久化。M7-T02 的多 NPC Scene 可以消费该快照，但不能让 Scene 或 UI 列表反向替代人口 authority。

## 12. Multi-NPC Scene 逐 Actor 提案

M7-T02 的 `PROPOSE_TAVERN_SCENE_ACTION` 复用唯一桌面 Provider/Prompt/schema 编排，但一次请求只接收一个 Actor 的 LOD、Goal、Knowledge 与 Memory。其他参与者只以公开身份和 Scene status 出现；Actor 输出只能引用自己的 Knowledge 白名单。Windows 可并发生成相互隔离的提案，Native 必须从 SQLite 重新构造每份输入并验证 generation audit。最终 speaker/action 由本地规则一次仲裁并与全部 proposal、generation provenance 和 scene revision 原子提交，Generator 不能直接选择或修改事实。

## 13. Immutable NPC Timeline 技术重试

M7-T03 在 Provider 调用前把单 NPC 或多 NPC Scene 的玩家意图、点名对象、可选硬结果引用和 Attempt 审计写入 schema 21。成功输出只能与 pending request、generation record、消息或 Scene Turn 在同一 Native 事务提交；已提交 Operation 不再进入 Generator。网络、Provider 可用性、结构、重复、应用中断和明确事实冲突可在同一 Operation 下创建新 Attempt，使用新 request/generation ID 但保留稳定 idempotency key、原意图、Actor 顺序和硬结果。认证、配额、规则、持久化与未知失败终止时间线，调用者不能放宽 Native Retry policy。完整合同见 [`V0.3_IMMUTABLE_NPC_TIMELINE.md`](V0.3_IMMUTABLE_NPC_TIMELINE.md)。
