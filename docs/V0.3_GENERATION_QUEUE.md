# Ember Tavern V0.3 Generation Queue

## 1. 调度合同

`packages/ai-core/src/generation-queue.ts`提供有界的P0/P1/P2调度器。Queue只调用注入的`execute`回调，不持有Provider、Prompt、Repository或SQLite，因此不会形成第二套模型栈。

- P0：玩家正在等待的NPC回复、行动和D20叙事。
- P1：即将使用的任务、NPC详情和当前地点。
- P2：预生成NPC、地点扩展、世界事件和职业池等后台工作。

全局并发限制为1–8，pending上限为concurrency–256。concurrency大于1时，P2最多占`concurrency - 1`个槽，始终为P0/P1保留前台容量。P0优先，但连续4个P0后若低优先级仍等待，会轮转执行一个P1/P2；P1/P2自身轮转，避免后台永久饥饿。Queue没有无限后台生成入口。

## 2. 去重、取消和超时

同一`intentKey`在queued/running期间返回同一个handle和Promise，只执行一次。任务完成、失败或取消后释放intent，后续新意图可重新入队。队列和运行中任务都可取消；运行中取消会abort当前attempt，迟到resolve/reject因单次settle保护被忽略。

`timeoutMs`是包含所有attempt的整体deadline，而不是每次重试重置的预算。超时会abort当前attempt并终止，不在过期deadline后继续retry/fallback。取消或超时本身不提供persist端口；实际生成器只有成功返回后才能进入M3-T01的rules/persist事务，因此不会产生部分事实。

## 3. Retry、Fallback和硬结果

每次execute收到`{ attempt, route, signal, hardResultKey }`。技术retry最多0–3次且只依据M1-T03稳定错误策略；达到retry上限后，只有`fallbackEligible`且调用方显式`allowFallback`才执行一次FALLBACK。认证、额度、Rule、Persistence和非瞬态Generation错误不能跨Provider绕过。

`hardResultKey`在PRIMARY、RETRY和FALLBACK之间按原值传递。Queue不生成或修改D20/规则结果，调用方必须用此键重新读取已锁定事实；测试验证技术重试和fallback都不能替换硬结果身份。

## 4. 指标与隐私

每个终态产生一条有界、内容无关的metric：task、priority、status、finalRoute、attempts、queueWaitMs、durationMs和安全errorCode。指标不含job/intent/request ID、Prompt、Context、玩家输入、响应文本、模型秘密或hardResultKey；时长被限制在0–86400000ms。

Queue不负责上传或写数据库；调用方可把metric接入M1-T04性能合同。取消、超时、失败和成功都产生一次终态metric，迟到结果不会产生第二条。

## 5. 验证

测试覆盖P0优先与四次burst公平性、P1/P2轮转、P2前台槽保留、全局并发、intent去重、queued/running取消竞态、整体timeout、有限retry、fallback资格、认证/规则拒绝、硬结果键不变、容量/配置边界以及内容无关指标。
