# Ember Tavern V0.3 Unified Context Builder

Status: M9-T01 implementation contract

Global visual standard: [`EMBER_TAVERN_VISUAL_STYLE_GUIDE_V1.md`](EMBER_TAVERN_VISUAL_STYLE_GUIDE_V1.md)

## 1. One shared boundary

Every production Generator reaches one shared Context boundary before prompt formatting:

```text
Task adapter / Native preparation
  → Unified Context Builder
  → Context Assembly + auditable Manifest
  → Prompt Manager / stable prefix
  → primary, fallback, or structural repair
```

Windows world, character, tavern, NPC dialogue, dialogue suggestion, Tavern Scene, Quest, Dynamic Quest, Adventure, settlement, NPC LOD, location, faction, and universal-character services all use `DesktopAIEngine`; its production orchestrator builds the unified context exactly once. Application turn orchestration and the primary AI task helper use the same builder. Primary/fallback/repair therefore receive the same frozen projected input and cannot select different facts on retry.

Existing NPC, Adventure, and World Event builders remain domain adapters: they enforce actor/campaign ownership and convert SQLite entities into minimal task fields. They are not page-specific context stacks. Retrieval scoring remains replaceable and M9-T03 will supply richer relevance signals through the same interface.

## 2. Closed layer order

The shared order is:

```text
SYSTEM
→ CONSTITUTION
→ LORE
→ LOCATION
→ PLAYER
→ ACTOR_KNOWLEDGE
→ QUEST_STATE
→ MEMORY
→ RECENT
→ ACTION
```

`SYSTEM` contains only the task identity and Context contract version. The remaining top-level task fields are classified by one closed taxonomy into existing Context block types. Constitution and task identity are stable; relevant lore, location, player, actor knowledge, Quest/world state, and long-term memory are semi-stable; recent interaction and current action are dynamic. Entity `revision` or `schemaVersion` is used as the block source revision when present; otherwise the caller's frozen source revision is retained.

The builder returns both the projected JSON task input and its immutable `ContextAssembly`. It never changes output schemas, Rules authority, Generator validation, or SQLite commit contracts.

## 3. Relevance, budget, and omission

Current domain adapters already remove other-Campaign entities, unrelated NPC messages/memories, unauthorized facts, excluded secrets, unrelated Quest/NPC records, and old history beyond bounded windows. The unified builder adds one common optional-field relevance contract:

- adapters may declare a field optional and provide a `0..1` relevance score;
- optional fields below the threshold are omitted as `not_relevant`;
- an optional block over its local limit is omitted as `block_budget`;
- an optional block that would exceed the total limit is omitted as `total_budget`;
- required SYSTEM/current task fields fail closed instead of being truncated or silently removed.

The final projected input must still pass the existing per-task character budget. JSON blocks are never sliced into invalid fragments. Manifest entries record block type, source, revision, stability, content hash, token estimate, relevance, required/included state, and exact omission reason without embedding content.

## 4. Knowledge and secret isolation

Actor Knowledge and Memory sources are privacy-classed `secret`, so the Context Inspector masks their source identifiers. Manifest and metrics never contain block content. The builder recursively rejects credential-shaped fields (`apiKey`, access token, credential ref, authorization, cookie, password, token) before prompt construction.

The builder also rejects explicit whole-database envelopes such as `database`, `databaseDump`, `sqliteDump`, `tables`, `allRows`, and `allData`. This is a boundary guard, not a substitute for repository relevance queries. NPC secrets that are part of an authorized actor profile remain game content; API credentials never do.

## 5. Audit and persistence

Desktop Context Inspector projects the actual unified manifest and retains only hashes and metadata. Application generation audit persists the same manifest inside the existing `generation_records.request_json`; no new SQLite table or schema migration is required. The existing stable cache prefix remains byte-stable because dynamic player input is still outside the stable Prompt profile.

M9-T01 does not create Summary or Long-term Memory truth, promote knowledge, or introduce vector retrieval. Those contracts belong to M9-T02 and M9-T03. It adds no UI/CSS; future inspector presentation continues to use existing Design Tokens and M10-T07 migration gates.

M9-T02 supplies source-backed Summary, current Actor Long-term Memory, and World Lore artifacts through the same layer taxonomy. Repository projections exclude stale source snapshots before the unified builder sees them. M9-T03 now selects Lore through explainable triggers, priority, score and budgets, then injects its bounded selection through the existing `LORE` field; it does not add a parallel Context stack or change this authority boundary. See [`V0.3_MEMORY_LAYERS.md`](V0.3_MEMORY_LAYERS.md) and [`V0.3_WORLD_INFO_RETRIEVAL.md`](V0.3_WORLD_INFO_RETRIEVAL.md).
