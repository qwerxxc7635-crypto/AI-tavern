# Ember Tavern V0.3 NPC LOD

## 1. 目标与边界

NPC LOD 用按需具体化替代“创建世界时生成完整人口”。系统只在明确需要一个背景人物时创建单个 LOD0 身份；观察、互动和持续进入剧情分别只允许晋升一级。世界创建、World Seed、Tavern 固定纵向切片和既有完整 NPC 合同保持不变。

NPC LOD 是 SQLite 中独立的、版本化的身份投影，不是 UI 临时列表，也不是第二套完整 NPC 真相。既有 `npcs` 行在 migration 16 中保守投影为 LOD3；之后既有流程新增的完整 NPC 由同一 SQLite 事务触发生成 LOD3 投影。低 LOD 身份只存在于 `npc_lod_profiles`，不会用空字符串或伪造文本填充旧 `npcs` 的非空字段。

## 2. 四级合同

| Level | 可持久字段 | 禁止提前出现 |
| --- | --- | --- |
| LOD0 | 不可变 identity anchor、背景人口角色、Constitution 证据 | 名字、外貌、行为、职业、事实引用及深层历史 |
| LOD1 | LOD0 + 名字、外貌、当前行为 | 职业、人格、目标、知识、关系及深层历史 |
| LOD2 | LOD1 + 职业、人格、目标、已授权 Truth ID 与 NPC 关系 ID | 记忆、秘密、Quest、装备、经历 |
| LOD3 | LOD2 + 已授权记忆、秘密 Truth、Quest、装备和经历 ID | 无额外级别；不可再次生成 |

所有 ID 列表都有上限、去重和 campaign 归属校验。`identityAnchor`、`populationRole`、campaign、Constitution revision 与创建时间终身不可变；已经非空的文本和已经存在的 ID 只能保留，不能改写或删除。

## 3. 晋升规则

唯一合法序列为：

```text
LOD0 --OBSERVED--> LOD1 --INTERACTED--> LOD2 --RECURRING--> LOD3
```

每次晋升必须满足：

- `lod + 1` 与 `revision + 1`，禁止跳级、降级和 LOD3 重生；
- Generator 输入中的 current profile、trigger、Constitution 证据和引用白名单必须与 Native 从当前事务重新构造的值完全一致；
- 输出逐字重复已存在身份字段和 Constitution 证据；
- 输出引用只能从本地白名单选择，不能创造 Truth、Claim、Memory、关系、Quest、Item 或 Event；
- generation audit、profile 更新和 append-only transition 在同一 `BEGIN IMMEDIATE` 事务提交；
- expected revision 仲裁并发；idempotency key 重放不增加 revision 或 transition。

TypeScript contract/Domain validator 用于生成前后快速反馈；Rust Native 与 SQLite trigger 是桌面事实提交边界。AI 的 schema validation 不等于业务接受，也不获得数据库写权限。

## 4. 知识边界

LOD2/3 的 `knowledgeFactIds` 只来自该 NPC 的 `actor_knowledge` 中 `KNOWN` Truth；`secretFactIds` 还必须对应 `SECRET` World Truth。Memory 必须属于同一 actor。低 LOD NPC 作为合法 Actor 纳入既有 knowledge、memory 和 actor-sourced claim trigger，但这些 trigger 不允许跨 Campaign、跨 Actor 或不存在的引用。

关系候选只来自同 Campaign 的已持久 LOD 身份；Quest 必须发布给或关联该 NPC；Item 必须有该 NPC 的语义绑定；经历只来自明确引用该 NPC 的 Game Event。白名单为空是合法状态，Generator 不得为了填满 LOD 而编造引用。

## 5. Generator 与桌面接入

统一任务 `GENERATE_NPC_LOD` 复用既有 Provider、Prompt、schema registry、Context Budget、Generator Runner、缓存指标和 generation audit。Native 先返回 canonical generation input；Windows `NpcLodService` 执行结构生成并把完整 audit 交回 Native。相同 campaign/NPC 的同时晋升在服务内合并，跨窗口或进程竞争仍由 SQLite expected revision 裁决。

`npc_lod_seed` 只显式创建一个背景身份，绝不扫描或生成世界人口。当前任务只提供领域、持久化和桌面服务能力；M7-T01 才根据地点、时间、势力、事件和历史决定酒馆需要哪些临时或持久 NPC。

## 6. 持久化与兼容

schema 16 新增：

- `npc_lod_profiles`：当前 canonical profile、LOD、revision、Constitution binding 与 generation provenance；
- `npc_lod_transitions`：append-only before/after snapshot、trigger、generation record 与 idempotency key。

本地数据库关闭重开后身份、revision 和深度不变。既有完整 NPC 回填和后续自动投影不改变 `npcs`、Dialogue、Quest、Adventure 或 Tavern 的业务语义。portable `.emtavern` 对新增表的正式格式与历史 fixture 迁移仍由 M10-T05 统一处理，M6-T03 不提前升级归档格式。

## 7. UI 与后续边界

M6-T03 没有逐页返工已完成 UI。后续自然展示 LOD 时必须复用现有 Design Token、UI Primitive 与 NPC Game Component，并保持 AI 为“命运 / 世界生成系统”的视觉身份。完整 Feature Page 与 Legacy UI 迁移仍由 M10-T07 和最终视觉审查执行。

本任务不实现动态地点、势力行动、酒馆动态人口选择、多 NPC 场景或不可变 NPC 时间线；这些继续严格属于 M6-T04、M6-T05 和 M7。
