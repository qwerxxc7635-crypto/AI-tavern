Status: M9-T03 implementation contract

Depends on: [`V0.3_MEMORY_LAYERS.md`](V0.3_MEMORY_LAYERS.md), [`V0.3_UNIFIED_CONTEXT_BUILDER.md`](V0.3_UNIFIED_CONTEXT_BUILDER.md)

Global visual standard: [`EMBER_TAVERN_VISUAL_STYLE_GUIDE_V1.md`](EMBER_TAVERN_VISUAL_STYLE_GUIDE_V1.md)

## 1. Authority and port boundary

World Info retrieval selects source-backed `WorldLoreEntry` records; it does not create facts, grant Actor Knowledge, or mutate game state. The candidate-source port accepts one structured Campaign query and returns a bounded Lore corpus. The V0.3 SQLite adapter implements that port directly. A future lexical index, embedding index, or remote RAG adapter may replace candidate loading, but must return the same candidate contract and pass the same local selection, budget, authority, and validation rules.

No vector service is required for V0.3. Retrieval is not a copy of an external Lorebook format and imported material cannot become `WorldTruth` through this interface.

## 2. Structured query and rule

A query contains:

- exact Campaign ID;
- bounded normalized search text;
- closed entity references (`NPC`, `PLAYER_CHARACTER`, `FACTION`, `ITEM`, `WORLD_FACT`);
- exact Location and Quest IDs;
- minimum relevance score and total token budget.

Every referenced entity must exist in that Campaign. A Lore rule belongs one-to-one to an existing Lore entry and contains bounded keywords, entity/Location/Quest triggers, optional `alwaysActive`, `ANY` or `ALL` matching, priority, per-entry token budget, enabled state, revision, and update time. Rules require at least one trigger. SQLite and the repository both reject malformed JSON, cross-Campaign references, identity changes, and non-contiguous revisions.

## 3. Deterministic selection

The local domain selector is pure and stable:

1. stale source-backed Lore, missing rules, and disabled rules are excluded;
2. exact keyword boundaries prevent partial Latin-word matches, while CJK keywords use normalized substring matching;
3. entity, Location, Quest, keyword, and always-active matches produce named weighted evidence;
4. `ANY` accepts at least one configured match; `ALL` requires every configured trigger;
5. candidates sort by priority descending, score descending, then Lore ID ascending;
6. per-entry and total token budgets are enforced without truncating Lore text.

The result includes selected title/text plus revision, score, priority, and matched triggers. Its manifest includes every candidate with inclusion state and one exact reason: selected, stale source, not configured, disabled, no trigger match, below threshold, entry budget, or total budget.

## 4. Cache correctness

The application service uses a bounded 128-entry LRU by default. Its key is the SHA-256 digest pair of the canonical structured query and the complete candidate corpus. Lore content/revision, source freshness, rule content/revision, trigger input, score threshold, or token budget changes therefore produce a miss. Campaign-scoped explicit invalidation is also available. Cache entries are process-local accelerators only; SQLite remains authoritative and corpus loading is repeated before a hit is accepted.

## 5. Production integration

NPC dialogue is the first production consumer. Before building `NPC_REPLY`, the application derives the current NPC, Tavern Location, related non-terminal Quest IDs, and player message from existing repositories. Retrieval selections enter the existing unified Context Builder as `relevantLore`, which classifies them in the `LORE` layer. Context pressure removes oldest recent history/Memory first and then the lowest-ranked Lore; it never slices JSON.

`NPC_REPLY` input and Prompt contracts advance to v5. Lore is world context only and does not authorize an NPC to reveal facts absent from its Actor Knowledge. The reply output contract, repetition checks, request transaction, relationship proposal, Memory extraction, and immutable dialogue semantics are unchanged.

Other Generators may adopt the same port when naturally required by their own task, but M9-T03 does not add a second Context stack or pre-empt M10 work.

## 6. Persistence and recovery

Schema 29 adds `world_lore_retrieval_rules`. Internal snapshots include rules after Lore entries and restore/delete them in foreign-key order; older snapshot payloads treat the table as empty. Local reopen therefore preserves rule revisions and exact selection behavior.

Portable `.emtavern` remains format v2. Its schema-29 archive policy, old fixtures, cross-language migration, corruption/interruption recovery, and recovery UI remain one coherent M10-T05 change.

M9-T03 adds no UI or CSS. Any later World Info or Inspector UI must reuse existing Design Tokens and components; Legacy migration remains M10-T07.
