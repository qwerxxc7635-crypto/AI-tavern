# Ember Tavern V0.3 Lazy World Generation

Status: M10-T01 implementation contract

Depends on: [`V0.3_WORLD_INFO_RETRIEVAL.md`](V0.3_WORLD_INFO_RETRIEVAL.md)

Global visual standard: [`EMBER_TAVERN_VISUAL_STYLE_GUIDE_V1.md`](EMBER_TAVERN_VISUAL_STYLE_GUIDE_V1.md)

## 1. Core world boundary

A confirmed world is playable infrastructure, not a fully generated setting. Its durable core is the Campaign, locked World Constitution, World Seed, World Bible, outline Locations, and outline Factions. Confirmation creates a generation plan but does not create a Career Pool, Tavern, NPC roster, Quest, Item, detailed Location, or active Faction.

This keeps cold start bounded and preserves SQLite as the only source of game state. A plan is an execution intent, never a generated fact and never a placeholder artifact.

## 2. Materialization plan

Schema 30 stores one idempotent plan per Campaign/kind/target:

| Kind | Mode | Priority | Artifact requirement |
| --- | --- | --- | --- |
| `INITIAL_CAREER_POOL` | `ON_DEMAND` | P0 | committed `career_pools` row |
| `TAVERN` | `ON_DEMAND` | P0 | committed Campaign Tavern |
| `TAVERN_ROSTER` | `ON_DEMAND` | P0 | Tavern plus at least four NPCs, three Rumors, and two Clocks |
| `LOCATION_DETAILS` | `BACKGROUND_ELIGIBLE` | P2 | committed `DETAILED` Location expanded from the target |
| `FACTION_DETAILS` | `BACKGROUND_ELIGIBLE` | P2 | target Faction in `ACTIVE` state |

The roster plan depends on the Tavern plan. Location and Faction entries are only eligible plans in M10-T01; automatic prediction, admission, and execution belong to M10-T02 Prefetch. Quest, Item, and unrestricted NPC generation are deliberately absent from core bootstrap.

## 3. Durable lifecycle

The closed lifecycle is `PLANNED → RUNNING → SUCCEEDED/FAILED/CANCELLED`, with retryable `FAILED` or `CANCELLED` entries allowed to return to `RUNNING`. Each claim increments the attempt counter and binds an active run ID. Same-run claims are idempotent; another run cannot steal an active intent. Every change advances a compare-and-swap revision and appends an immutable transition with reason, run, error, retryability, and time.

SQLite success triggers verify the real artifact before accepting `SUCCEEDED`; writing a placeholder or merely receiving model output cannot complete a plan. Existing Career Pool, Tavern, roster, dynamic Location, and active Faction commit transactions reconcile their corresponding plan only after validated artifacts have been written. A Location plan targets an outline expansion origin and records one newly committed connected/child detailed Location as its artifact. Legacy Campaigns migrated to schema 30 but lacking bootstrap plans continue through their established commit paths.

## 4. Failure, cancellation, and reopen

A failed child materialization does not roll back or downgrade a completed core or sibling plan. Cancellation is durable and retryable. On reopen, a `RUNNING` plan is reconciled to success if its artifact was committed before response loss; otherwise it becomes retryable `FAILED/INTERRUPTED`. This makes process loss explicit without duplicating committed content.

Internal snapshots capture plans after their referenced world/artifact rows and transitions after plans. Restore uses the existing guarded restore session, preserves non-initial states and append-only history, and treats schema-30 tables as empty when reading an older payload.

## 5. Boundaries

- M10-T01 schedules no speculative background work and records no prefetch metrics.
- AI output remains an untrusted proposal and cannot mutate plan or world state directly.
- Rules Engine, D20, Provider, Generation Queue, Quest/NPC/Adventure contracts, and save format semantics are unchanged.
- Portable `.emtavern` remains format v2; schema-30 cross-language archive migration remains M10-T05.
- No UI/CSS is introduced. Future progress/recovery UI must reuse existing Design Tokens and components; Legacy migration remains M10-T07.
