# V0.3 Dialogue Suggestions

## 1. Scope

M7-T04 adds three to five optional dialogue suggestions to the existing `ActionComposer` for a single NPC dialogue and an active multi-NPC Tavern scene. Suggestions are derived UI assistance: selecting one only fills the editable draft and, for a scene, its optional addressed NPC. The player must still submit explicitly, and free input remains available when generation is loading, cancelled, invalid, or unavailable.

This task does not add Swipe, auto-send, Prompt Manager, a second composer, a new visual system, or any authority to change NPC, Quest, Rules, D20, world, or timeline state.

## 2. AI contract and knowledge boundary

`GENERATE_DIALOGUE_SUGGESTIONS` version 1 accepts only player-visible context:

- world summary and current region;
- player name, concept, and goal;
- public participant identity and scene status;
- the target NPC relationship scores for a single dialogue;
- recent public dialogue or selected scene actions;
- currently open Quest identifiers, titles, and statuses.

NPC secrets, private Knowledge, Memory, hidden Quest data, unrevealed World Facts, and other Actors' private state are excluded. The output is a strict, unique list of three to five `{text, addressedNpcId}` candidates. Native validation rejects an unknown addressee and requires the sole NPC as addressee in a single-NPC scope.

## 3. Canonical context and invalidation

Native rebuilds the input from SQLite and computes a SHA-256 context digest over the campaign identity, public input, and local invalidation signals. Signals cover the target NPC/relationship/conversation or Tavern scene revision plus Campaign state, World Facts, Clocks, active Factions, current Location state, Tavern population, latest Event, and open Quests.

The cache key is exactly `(campaign, scope kind, scope id, context digest)`. A changed signal produces a new digest, so an old row cannot be returned for the current world. Cache rows are immutable derived records; they are not `ai_candidates`, Messages, Scene Turns, Game Events, or player actions.

## 4. Generation and commit

Windows first prepares the canonical input. An exact cache hit returns without calling the model. A miss runs the shared desktop AI pipeline, validates the strict output, checks cancellation, then sends the generation audit and expected digest to Native.

Native opens an immediate transaction, rebuilds the context, and rejects a stale digest or altered input with `FACT_CONFLICT`. It atomically stores the pending request audit, generation record, and immutable cache row. Concurrent equivalent commits serialize and reuse the first exact cache. Cancellation or any generation/schema error before commit leaves SQLite unchanged; a late response after page cancellation is never committed.

## 5. UI and visual boundary

`NpcDialoguePage` and the multi-NPC section of `TavernPage` reuse the existing `ActionComposer`. Loading and retry are optional-assistance states, not blockers for the textarea. Selecting a suggestion copies its text to the draft; editing the multi-NPC draft clears the suggested addressee. Suggestions never invoke `send()` themselves.

The naturally touched UI continues to use existing Design Tokens and Game Components under [`EMBER_TAVERN_VISUAL_STYLE_GUIDE_V1.md`](EMBER_TAVERN_VISUAL_STYLE_GUIDE_V1.md). M7-T04 adds no CSS and does not perform Legacy UI migration; broader convergence remains M10-T07.

## 6. Verification

Tests cover strict count, public relevance inputs, single and multi-NPC composer integration, permanent free input, exact cache reuse, world/context invalidation, unknown addressee, stale commit, cancellation, error cause preservation, no auto-send, and absence of player-action persistence.

Portable `.emtavern` format v2 is unchanged. Schema 22 local cache export/import policy remains part of M10-T05.
