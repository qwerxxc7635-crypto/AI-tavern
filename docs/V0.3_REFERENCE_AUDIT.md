# Ember Tavern V0.3 — GitHub Reference Audit

审计日期：2026-08-13

## 1. 方法与结论摘要

本审计只使用项目官方 GitHub 仓库、官方文档和仓库 License 作为主要证据。研究目的是找到可验证的设计思想，而不是选择一个项目整体迁移。每个参考项目都按“研究模块、优点、缺点、Ember 适用性、是否采用、拒绝原因”记录。

总体结论：

- 保留 Ember V0.2 的 Tauri + React + Rust + SQLite + Zod/领域规则架构，不迁移到完整游戏引擎、Agent 框架或 Web 服务器。
- 从 SillyTavern / RisuAI 学角色扮演产品能力，但不复制 GPL/AGPL 实现、可刷新正式时间线或开放插件执行面。
- 从 TypeChat 学 schema-first parse/validate/repair，从 LangGraph/XState 学可恢复阶段图和可测试状态机，但优先扩展现有轻量编排，不直接引入重量框架。
- 从 Evennia/Bevy 学数据驱动实体与逐步具体化，从 Ink 学版本化故事/存档和后果表达；拒绝固定作者脚本成为 Ember 的世界主线。
- 从 Actual Budget、SQLite/rusqlite 学 local-first、迁移、备份和数据库事实边界；不同步到云端。
- 从 Radix Primitives 学无障碍行为合同和 headless composition；Ember 保持自己的视觉体系。

## 2. 参考项目

### 2.1 SillyTavern

- **项目 / GitHub**：[SillyTavern/SillyTavern](https://github.com/SillyTavern/SillyTavern)
- **License**：GNU AGPL-3.0。
- **研究模块**：Character Card、Persona、World Info、Prompt Manager、Preset、Chat、Group Chat、Context/Memory、Branch/Checkpoint、Model Settings、Import/Export、Extension、生成 UX。
- **优点**：角色扮演上下文控制面成熟；角色/玩家/Lore/Prompt/历史可组合；多 Provider 与高级用户配置丰富；聊天生成反馈、导入导出和扩展生态完整。
- **缺点**：强可变聊天语义允许 Swipe、Regenerate、编辑/删除历史；复杂设置学习成本高；第三方扩展扩大供应链和凭据风险；文件/聊天中心状态不等同于规则化 RPG 事实库。
- **Ember 适用性**：高，适合作为 Roleplay 产品能力上限参考；不适合作为 Rules/SQLite 架构模板。
- **采用判断**：**采用产品思想，不采用代码**。具体取舍见 `docs/V0.3_ST_FEATURE_MATRIX.md`。
- **不采用原因**：AGPL 边界；正式游戏事实不可 Swipe；Ember 不开放任意第三方代码执行，也不复制 UI/品牌/素材。

### 2.2 RisuAI

- **项目 / GitHub**：[kwaroran/RisuAI](https://github.com/kwaroran/RisuAI)
- **License**：GPL-3.0。
- **研究模块**：跨端 AI Roleplay、Character Card import/export、Lorebook、Prompt、Provider、插件和移动/桌面产品组织。
- **优点**：相对一体化、用户友好的 Roleplay 前端；Character Card/Lorebook 兼容性广；TypeScript/Svelte 跨端实现可观察；发布迭代频繁。
- **缺点**：仍以聊天和 Prompt 可塑性为中心；插件/脚本能力会扩大攻击面；GPL 代码不可直接并入不兼容分发；其 Svelte/Capacitor 结构与 Ember 现有 React/Tauri/Rust 不匹配。
- **Ember 适用性**：中高，适合交叉验证 SillyTavern 不是唯一可行 UX，尤其是角色资产和移动布局。
- **采用判断**：**采用格式/交互思想，不采用实现或技术迁移**。
- **不采用原因**：GPL、技术栈迁移收益不足、聊天时间线与 Ember 硬事实语义不同；V0.3 不做完整卡格式矩阵或插件生态。

### 2.3 Tauri

- **项目 / GitHub**：[tauri-apps/tauri](https://github.com/tauri-apps/tauri)
- **License**：MIT OR Apache-2.0；官方[架构文档](https://github.com/tauri-apps/tauri/blob/dev/ARCHITECTURE.md)说明 Rust core、WebView、WRY/TAO 和消息桥接。
- **研究模块**：桌面壳、Rust/WebView 权限边界、命令、平台打包、生命周期和更新。
- **优点**：系统 WebView、较小包体、Rust 原生能力、命令/Capability 模型、跨 Windows/macOS；与 Ember V0.2 实际门禁一致。
- **缺点**：平台 WebView 行为存在差异；跨平台发布仍需各平台真实构建；WebView 不能被当成可信原生进程。
- **Ember 适用性**：极高，已经是现有桌面基础。
- **采用判断**：**继续采用并深化**。高权限 Credential、文件、HTTP、SQLite 和生命周期留在受限原生层。
- **不采用原因**：不启用任意 shell/HTTP/文件插件；不因 Tauri 支持移动端就提前全面开发 iOS。

### 2.4 Actual Budget

- **项目 / GitHub**：[actualbudget/actual](https://github.com/actualbudget/actual)
- **License**：MIT。
- **研究模块**：local-first 应用、共享 core/desktop 分层、SQLite、迁移、投影和长期本地数据演进；官方[数据库说明](https://actualbudget.org/docs/contributing/project-details/database/)确认数据本地存于 SQLite。
- **优点**：成熟的本地优先产品；SQLite 长期演进、跨平台 core 和用户数据迁移问题与 Ember 相近；真实世界中重视数据不丢失。
- **缺点**：金融账本和同步模型与 RPG 不同；项目规模和同步复杂度高；Electron/Node 结构不能直接套用 Tauri 原生边界。
- **Ember 适用性**：高，适合迁移、兼容视图、local-first 和数据生命周期参考。
- **采用判断**：**采用数据演进思想，不采用同步栈**。
- **不采用原因**：V0.3 不做云同步/CRDT；不能为借鉴 local-first 而引入其应用框架或账本模型。

### 2.5 SQLite / rusqlite

- **项目 / GitHub**：[sqlite/sqlite](https://github.com/sqlite/sqlite)、[rusqlite/rusqlite](https://github.com/rusqlite/rusqlite)
- **License**：SQLite 核心 Public Domain（仓库构建辅助文件有少量 BSD-style 例外）；rusqlite MIT。
- **研究模块**：事务、WAL/备份、完整性、版本迁移、Rust 绑定和 bundled SQLite。
- **优点**：单文件、ACID、成熟、适合桌面本地事实；rusqlite 提供受控 Rust API、backup 等 feature；与现有 Ember 原生层一致。
- **缺点**：Schema 迁移、连接并发和 JSON 内引用仍需应用自行保证；bundled/system SQLite 选择影响构建；不是自动事件溯源或业务验证器。
- **Ember 适用性**：极高，已经是唯一事实库。
- **采用判断**：**继续采用**，扩展 save/world schema version、隔离副本迁移、完整性与领域重载。
- **不采用原因**：不开放 loadable extension、任意 SQL 或 WebView 连接；不把 JSON blob 当免验证的数据捷径。

### 2.6 Microsoft TypeChat

- **项目 / GitHub**：[microsoft/TypeChat](https://github.com/microsoft/TypeChat)
- **License**：MIT。
- **研究模块**：schema-first LLM 输出、parse、validation、repair、意图确认。
- **优点**：明确把自然语言输出约束到类型；失败时生成 repair prompt；判别联合适合实体/动作提案；与 Ember 的 Zod/Structured Output 方向高度一致。
- **缺点**：解决的是自然语言到类型，不处理 RPG 业务规则、事务、Provider 队列、世界事实授权或 Rust 双实现；生成 schema prompt 可能扩大 token。
- **Ember 适用性**：高，适合 Generator 的 parse/validate/repair 阶段。
- **采用判断**：**采用生命周期与测试思想，暂不引入依赖**。
- **不采用原因**：Ember 已有 task schema、validator 和 repair；直接加入另一层会重复抽象。后续只有证据显示能减少维护成本才引库。

### 2.7 LangGraph.js

- **项目 / GitHub**：[langchain-ai/langgraphjs](https://github.com/langchain-ai/langgraphjs)
- **License**：MIT。
- **研究模块**：状态图、durable execution、checkpoint、interrupt/resume、streaming、human-in-the-loop。
- **优点**：把多阶段工作流显式成图；持久 checkpoint 和恢复语义成熟；适合观察 Generator Queue、repair 和人工确认的可能设计。
- **缺点**：为通用 Agent/tool workflow 设计，依赖面和抽象成本高；checkpoint 数据可能增长；框架状态不能替代 Ember SQLite 事实和领域事务；resume/部署语义有额外复杂性。
- **Ember 适用性**：中，适合作为可恢复 workflow 参考，不适合作为事实库或 World Director。
- **采用判断**：**借鉴 durable graph/interrupt 思想，不采用框架依赖**。
- **不采用原因**：现有 pending request、SceneFrame、snapshot 和 SQLite transaction 已覆盖关键语义；V0.3 应先扩展轻量 Generator 状态机，避免第二套 checkpoint 真源。

### 2.8 XState

- **项目 / GitHub**：[statelyai/xstate](https://github.com/statelyai/xstate)
- **License**：MIT。
- **研究模块**：statechart、actor、事件驱动、guard/effect、inspection 和 model-based testing。
- **优点**：复杂 UI/工作流状态显式、可视、可遍历测试；React 集成成熟；适合 Character Creation、Action Composer、Generation Queue 的 race/cancel 状态分析。
- **缺点**：actor 状态容易被误用成业务事实；引入库会与现有手写状态机并存；视觉工具不是产品正确性的保证。
- **Ember 适用性**：中高，尤其适合临时 UI/请求状态，不适合 SQLite 事实。
- **采用判断**：**采用状态图和 model-based test 方法；是否引库在具体任务以复杂度证据决定**。
- **不采用原因**：不进行全仓状态管理迁移；Zustand/React/XState 均不得保存 Campaign 真相。

### 2.9 Evennia

- **项目 / GitHub**：[evennia/evennia](https://github.com/evennia/evennia)
- **License**：BSD-3-Clause。
- **研究模块**：长期运行文字世界、对象/地点/角色、命令、定时任务和 genre-agnostic MUD 框架。
- **优点**：真实成熟的持久文字世界；实体、地点、行为和世界 tick 分离；不预设特定游戏类型；适合验证“世界不是聊天记录”的观念。
- **缺点**：Python/Django/Twisted、多用户服务器和命令解析器与 Ember 单人桌面技术栈差异大；服务器常驻/实时世界不是 V0.3 目标。
- **Ember 适用性**：中高，适合 Dynamic Entity、Location、Faction 和 World Director 领域建模参考。
- **采用判断**：**采用数据驱动对象和延迟具体化思想，不采用框架**。
- **不采用原因**：不引入服务器、网络、多用户、Python runtime 或传统命令 parser；后台世界变化必须受预算且持久化。

### 2.10 ink

- **项目 / GitHub**：[inkle/ink](https://github.com/inkle/ink)
- **License**：MIT。
- **研究模块**：分支叙事、变量/条件、choice、story/save format version、运行时状态和测试。
- **优点**：成熟的可组合分支与后果表达；故事格式和存档格式明确版本化；编译/运行时边界清楚；适合 Quest Graph 的可测条件和 consequence 思考。
- **缺点**：核心是作者预先编写的 narrative script；没有完整世界对象模型；固定 flow 与 Ember“世界适应玩家、无固定主线”冲突。
- **Ember 适用性**：中，适合 Quest 条件/后果和版本化格式参考，不适合作为内容引擎。
- **采用判断**：**采用可测试图、条件和版本化思想；拒绝固定脚本核心**。
- **不采用原因**：V0.3 Quest 由世界事实、玩家行为和 Director 动态产生；不能把 AI 输出编译成绕过 Rules 的脚本。

### 2.11 Bevy

- **项目 / GitHub**：[bevyengine/bevy](https://github.com/bevyengine/bevy)
- **License**：MIT OR Apache-2.0（个别文件/示例资产需单独核对）。
- **研究模块**：ECS、数据驱动实体、system schedule、state、modular plugin、资源。
- **优点**：实体与组件组合、系统只读取所需数据、调度和模块化清晰；适合思考 NPC LOD、地点、势力、状态效果和 World Director 的数据依赖。
- **缺点**：完整实时 2D/3D 游戏引擎远超文字桌面应用需要；API 迭代快；ECS 会增加 SQLite 映射、调试和迁移复杂度。
- **Ember 适用性**：概念层中等，依赖层低。
- **采用判断**：**只采用按需组件化和 system input 最小化思想，不引入 Bevy/ECS**。
- **不采用原因**：当前聚合/Repository 足以表达 V0.3；不为尚未证明的规模问题重构成 ECS，也不引入渲染/实时循环。

### 2.12 Radix Primitives

- **项目 / GitHub**：[radix-ui/primitives](https://github.com/radix-ui/primitives)
- **License**：MIT。
- **研究模块**：headless React primitives、accessibility、focus/keyboard、composition、incremental adoption。
- **优点**：无样式、可渐进采用；封装 Dialog/Tabs/Tooltip 等复杂键盘、焦点和 ARIA 行为；允许 Ember 自建视觉 token。
- **缺点**：不是完整 Design System；依赖和 bundle 仍需按组件评估；桌面 WebView、复杂游戏布局和视觉回归仍需 Ember 自测。
- **Ember 适用性**：高，适合 M2 UI Primitives 的行为基线。
- **采用判断**：**采用 headless/a11y 行为合同；是否直接依赖逐组件评估**。
- **不采用原因**：不复制其网站/示例视觉；不把组件库通过视为 Ember WCAG 或四分辨率验收完成。

## 3. 子系统选择

| Ember 子系统 | 主要参考 | 采用内容 | 明确不采用 |
| --- | --- | --- | --- |
| Roleplay / Character / Lore | SillyTavern、RisuAI | 产品能力矩阵、scope、Prompt 可观察性、资产 UX | GPL/AGPL 代码、品牌/UI、正式事实 Swipe、开放插件 |
| Generator / Structured Output | TypeChat、LangGraph.js | schema-first parse/validate/repair、显式阶段、interrupt/resume 思想 | 第二套 Agent/checkpoint 真源、通用 tool agent |
| UI / Request State | XState | 状态图、guard、race/cancel、model-based tests | 全仓状态管理迁移、actor 成为事实库 |
| Dynamic World / Entities | Evennia、Bevy | 数据驱动实体、地点/行为分离、LOD/最小 system input | MUD server、多人、Python runtime、完整 ECS/game engine |
| Quest Graph | ink、XState | 可测试条件/后果、图遍历、格式版本 | 预写固定主线、脚本绕过 Rules |
| Desktop / Native Security | Tauri | Rust/WebView 权限边界、Capability、平台构建 | 任意原生命令、提前全面 iOS |
| Local-first / Persistence | Actual Budget、SQLite/rusqlite | SQLite 唯一事实、迁移/备份、兼容投影、长期本地数据 | 云同步、CRDT、WebView SQL、loadable extension |
| Design System | Radix Primitives | headless composition、keyboard/focus/ARIA 行为基线 | 复制视觉、用库替代产品可访问性验收 |

## 4. License 与复制策略

- GPL/AGPL 项目：只做 clean-room 产品/架构研究；不复制源码、CSS、文案、图标、素材或可识别实现片段。
- MIT/BSD/Apache/Public Domain 项目：License 允许不等于应当复制。优先使用公开 API 的正式依赖；任何代码/资产引入需登记精确包、版本、License 和 notices。
- 示例资产、字体、图标和默认内容常与主仓库代码 License 不同，默认不引入。
- 本审计不构成法律意见；发布前仍需执行依赖/资产 License 清单和安全审计。

## 5. Final Decision

V0.3 不做框架大迁移。现有 Ember 架构继续作为主干：Tauri 原生安全边界、共享 TypeScript 合同/领域、Rust 原生事务、SQLite 唯一事实、统一 Provider 和可审计 Context。新能力按问题驱动逐层加入。

优先落地顺序与 `docs/TASKS.md` 一致：先修 Credential/Navigation/Error/Performance，再做 Design System，然后增加 Generator/Queue/Schema/Inspector。只有在具体任务的测试证明现有轻量实现无法安全表达复杂度时，才评估 XState、Radix 或其他 permissive dependency；LangGraph、Bevy、Evennia、Ink 不作为 V0.3 runtime dependency。
